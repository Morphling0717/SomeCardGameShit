# 架构说明

## 目标

第一版采用“规则核心与表现层分离”的结构：

```text
卡牌定义 / 后续 Lua 脚本
          ↓
确定性规则核心（唯一合法性来源）
          ↓
对局事件与选择请求
          ↓
YGOPro2 客户端兼容层
          ↓
场面、UI、动画、声音与网络输入
```

当前仓库先完成中间的规则核心。它不是为了绕开 YGOPro，而是为了在修改 `ocgcore` 和 YGOPro2 前建立一套可以自动验证的行为规格。

## 核心对象

### `CardDefinition`

保存不会在对局中改变的卡牌数据：类型、费用、基础攻击与生命、特征、关键词、印刷素材印记、效果和高级召唤条件。

### `CardInstance`

保存对局中的卡牌实例：所在区域、控制者、当前攻击、当前生命、生命上限、进化状态、临时突进、是否于本回合高级召唤，以及后天继承的素材印记。

印刷印记只存在于 `CardDefinition`，继承印记只存在于 `CardInstance`。高级召唤选择印记时只读取前者，因此不会发生二次继承。

### `PlayerState`

保存主战者生命、PP、进化点、回合计数、每回合限制，以及牌组、手牌、单位区、战术区、墓地、封存区和召唤牌组。

### `Game`

唯一允许改变对局状态的入口。客户端不能自行扣 PP、移动卡牌或判断可否攻击，只能提交命令并读取结果。

## 操作事务

每个公开操作遵循：

1. 检查比赛和阶段；
2. 检查控制者、区域、费用、目标和次数限制；
3. 在验证完成后才支付成本；
4. 完整处理当前动作；
5. 同批单位全部离场；
6. 处理遗言等触发；
7. 检查主战者胜负；
8. 必要时打开一个伏策窗口；
9. 输出事件。

无效操作原则上不得改变状态。针对费用不足、错误目标、重复素材等情况已有回归测试。

## 同时死亡

同一次战斗或效果使多个单位生命归零时：

1. 先收集整批死亡单位；
2. 按当前回合方、非当前回合方的顺序记录触发；
3. 整批单位先全部离场；
4. 再处理遗言与印记遗言；
5. 新死亡进入下一批。

同一玩家内部的人工排序尚未接入客户端，当前以场地顺序作为确定性占位。YGOPro2 接入时会增加排序请求，不能把当前占位当成最终交互。

## 测试不变量

`Game::validate_invariants()` 检查：

- 每张卡恰好位于一个区域容器；
- 区域、控制者和序列一致；
- 单位与战术卡类型正确；
- 单位战斗数值有效；
- PP、生命、手牌和计数器不越界；
- 继承印记不会残留在场外；
- 反应阶段与待处理反应一致；
- 胜负结果与阶段一致。

烟雾对局在每一个动作后执行这套检查。
